# Proposed trace ownership and delivery contract

Status: proposed design and test requirements, not an implemented or measured guarantee. The CPU-only traced-worker bridge and host trace store are standalone prototypes on development branches; the budgeted forward worker and IPC v1 are separate components. The proposed workflow is not wired end to end: BudgetedWorker does not admit tracing, and IPC v1 does not transport traces. Nothing in this document establishes GPU-safe concurrency or a bound on total machine RAM.

## Scope and accounting authority

A trusted in-process coordinator owns one ledger for every participating producer, store operation, serializer and delivery for a device/service instance. A claim is a unique capability tied to a request generation, buffer role, location and maximum logical bytes, not a naked byte count. Reserve before allocating; a failed reservation performs no payload or buffer allocation (reservation/error metadata may still allocate). Releasing one claim cannot release another, including on repeated release or stale handles. A claim may be indivisible: retain a group-envelope claim until every covered buffer is gone, and create separate claims for buffers needing independent release. Transfers change ownership atomically without a zero-claim interval. If a single ledger cannot atomically transfer, acquire the destination claim before releasing the source and reject if both cannot fit; this is a deliberate temporary conservative double reservation for one buffer, not a second physical allocation. All admissions and transitions are synchronized, and cleanup is idempotent. Per-request, per-batch and service-wide limits are hierarchical checks against the same underlying claims, not additive duplicate charges for one backing buffer.

Do not add separate local limits as if they were global: CaptureDispatcher's cap, HostTraceStore's cap and MemoryBudget's counters have different scopes. An authoritative aggregate host limit must include every concurrent request and distinguish trace snapshots from input, logits, metadata, encoder scratch and other host allocations. Logical payload claims exclude allocator rounding, Python overhead, library workspaces, unknown aliases, and OS/device allocations; conservative measured estimates and reserve are still needed and OOM can occur. A service-wide memory hard limit requires an OS-enforced process boundary and a policy for memory outside it.

The current MemoryLease couples GPU incremental estimate to outstanding host/gpu trace counters. For a safe initial integration, retain the entire lease until all claims are released, accepting that device admission remains blocked by slow consumers. To release device capacity earlier, implement a separate aggregate host ledger with atomically transferable host claims; do not call existing `lease.release()` with live trace claims and do not pretend the current lease has split semantics.

## Minimum allocation map

1. Before forward, reserve a trusted, server-configured worst-case capture envelope for each admitted request and the entire batch. The profile includes existing activations, GPU index tensors and index_select results, device-to-host staging and synchronization, host capture tensors, and any retained GPU copies. Requests cannot set their own resource estimates. Do not admit when the applicable per-request or aggregate limit cannot fit.
2. Count each distinct retained object or actual copy separately. With CPU capture, a 100-byte dispatcher source plus a 100-byte HostTraceStore clone requires two simultaneous 100-byte claims until the source is discarded. Each `read()` clone needs another claim before allocation. Shared references to the same storage may share one claim only when the coordinator controls every reference and lifetime; separately cloned aliases require distinct claims. Metadata-only events still consume an item slot.
3. Before store commit, reserve both the aggregate host-copy claim and the store's item/byte reservation. Failure to obtain either releases the other and creates no clone. Bind each claim to the exact store reservation generation; the current host store enforces only its own logical cap. Expose neither raw handles nor metadata to consumers before the batch postchecks and request-level publication transaction.
4. Before serialization or `read()`, reserve bounded extra capacity for the specific operation and retain the source claim while source bytes remain referenced. Prefer bounded binary chunks and reusable bounded scratch over `.tolist()` and whole-message JSON; v1 IPC currently expands logits into Python objects and multiple frame representations and is not a trace transport. If an encoder allocates variable Python objects, use a justified upper bound plus margin, or fail closed. A final wire-frame length check alone is too late to bound encoder allocations. Bound frame/chunk length, queued deliveries, concurrent readers, active request generations, operations, claims and item count. Zero-byte claims and cancelled generations must have bounded counts and a retirement path.
5. Returned buffers remain charged after `take()`: store accounting ends, but the authoritative claim transfers with the same storage to a result/delivery owner. The store and ledger use separate locks, so an operation guard must pin that claim across the entire take/handoff; serialize the guard completion and ownership transition under the request owner, or quarantine if their result is uncertain. `read()` leaves the store claim active and creates a separately charged clone. No quota is released merely because a counter says zero, a Python reference was reassigned, or a timeout occurred.

## Publication and cancellation

Use a unique `(broker lifetime, job generation, request, item)` identity and one lifecycle handle per generation. Stage immutable schema metadata and store handles privately. While claims remain pinned, validate matching IDs, shape/dtype and capture-time metadata, ensure all required items exist, and complete worker/model checks and any required CUDA drain. Then recheck cancellation and publish one immutable manifest under a request-lifecycle synchronization point; route each sample only to its authorized request. Do not hold the lifecycle lock across a forward, device drain, slow copy or socket operation. A failed or cancelled batch must not expose a partial trace as complete; the simplest first implementation cancels the whole in-flight batch if any participating request is cancelled. The winner of cancellation versus publication is the state transition taken under that same synchronization point; document treatment of cancellation after publication. A ledger operation finishing with a "live" status is only a snapshot and cannot substitute for this atomic publish-versus-cancel transition.

Cancellation first prevents new reservations and publication for that generation. It marks in-flight copies for rejection but does not uncharge them: wait for each producer/serializer to acknowledge termination, drop its owned buffers, and only then release its claims. A cancelled or disconnected client cannot make a still-running copy, kernel, or encoder disappear. CUDA claims and device leases survive until completion is synchronized and cleanup is verified. If completion, ownership, or hook cleanup is uncertain, quarantine the affected ledger/worker and retain claims until cleanup/device completion is established or the affected execution process has actually terminated; do not infer cleanup from a caught exception. Clear private result/slice locals before propagating retained exceptions, and use weakref tests to detect traceback-held tensors. A terminal job record must distinguish cancellation requested from cancellation fully drained.

## Delivery and acknowledgement

Keep IPC v1 forward-only. A trace-capable protocol needs a new version, authenticated and bound to broker lifetime, job/team, unique delivery generation and item/manifest identity. Explicit states are staged, ready, delivering, locally drained, acknowledged, released, or aborted. Reject stale, duplicate or cross-team acknowledgements without releasing another generation's claim; make exact duplicate release messages idempotent. Clients must not accept incomplete chunks as a complete trace.

Bound simultaneously active deliveries, chunk buffers, total encoded bytes and per-client outstanding deliveries; apply backpressure and finite deadlines. A receipt ACK says only that the peer claims to have received the data. A separate RELEASE ACK is a cooperative declaration that it has stopped using its delivery; it is not proof that its process freed the data or made no copies. After local send completes or aborts, drop service-owned serialization buffers and release their claims. Service-owned payload claims remain until their last service reference is disposed or an atomic transfer is complete. On timeout/disconnect, stop send, join encoder/copy work, dispose service-owned state, and release local claims only after verified cleanup. Any client copies, kernel socket buffers and unrelated processes are outside a process-local ledger; disconnect or ACK cannot prove their disposal. A genuine machine-wide bound requires controlled clients, OS-enforced process limits, and a verified process-lifetime policy, not just a protocol ACK.

## Required CPU tests before wiring

- Exact per-request and aggregate byte/item limits with zero-size and metadata-only events; reserve-before-copy; two requests contend; duplicate/aliased source tensors produce independent charged copies. Per-request and batch views must not double-charge the same backing storage in the global aggregate. Test caps and retirement for empty generations, claim/operation handles and clients.
- A source, store clone, two `read()` copies and encoder buffers coexist; check the ledger reaches their sum and admission rejects before allocation one byte beyond the cap. `take()` transfers the claim without an uncharged interval; double release and stale/foreign handles never release another claim.
- Inject failures and OOM at each reserve, capture, clone, metadata publication, serializer, partial-send, ACK, disposal and transfer step. Retain exception objects and verify no store/dispatcher-owned tensor survives uncharged via traceback; otherwise keep its claim and assert quarantine and no new admission until cleanup is verified.
- Cancel before forward, during index selection, while store copy is blocked, after store commit but before publication, during serialization, during partial send and after ready. Block copies with deterministic events: while blocked, quotas stay charged, no newer submission/publish for that generation succeeds, and claims return to zero only after join/verified disposal.
- Race two commits on one reservation, read vs take/drop, cancellation vs publication, duplicate/forged ACK, generation reuse, timeouts and disconnects. Assert each generation has at most one valid terminal result and exactly-once claim disposal. Check stale handles cannot access or free replacements.
- A partial batched trace failure or one cancelled row yields no successful partial manifest; no cross-request samples, metadata or claim ownership leak. Verify the owner prevents concurrent source mutation while copying; changed shape or size can be detected, but same-shape value mutation cannot be reliably detected after the fact.
- GPU-capable integration must separately demonstrate synchronized device drain, safe transfer lifetime and failure quarantine on the actual device before any GPU safety or throughput claim. CPU simulation alone is not that evidence.
