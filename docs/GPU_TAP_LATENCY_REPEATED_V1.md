# Repeated two-token GPU tap benchmark, proposed v1

**Status: proposal; implementation and required checks remain.** Freeze the
implementation, complete the checks below, and publish its exact source and
this protocol before any benchmark forward. The earlier
[two-token exploratory result](GPU_TAP_LATENCY_RESULTS.md) motivates this
repeat but is not a member of the new dataset.

## Question and scope

On one pinned DistilGPT2 checkpoint, input and host, describe the within-round
latency ratio of a local auxiliary-gradient activation readout to direct
activation capture. Also describe direct capture relative to no capture. The
experiment is a small host-specific comparison, not a general performance
claim, full-model backward benchmark, or model-sensitivity experiment.

Use the [previous reviewed two-token implementation](https://github.com/EastonSell/model-looking-glass/tree/616ff2d9bcc274587c650cdbb8e7a643f5f47a5f)
as the measurement-contract reference. Fix batch size 1, token IDs
`[15496, 995]`, model revision `2290a62682d06624634c1f46a6ad5be0f47f38aa`,
FP32, eager attention, eval mode, no KV cache, and the last-token output of
`transformer.h.0`. Keep the same three modes:

* `none`: model forward and finite-logit validation without a capture;
* `direct`: the same forward, a direct hook capture of one `1 x 1 x 768`
  float32 activation, and finite checks;
* `gradient`: the same location and output validation, using the prior local
  auxiliary `autograd.grad` readout and its clone, reduction and finite checks.

Direct/no-capture includes capture and activation-validation costs. The
gradient path is not a full-model backward pass. Preserve the v2 untimed
preflight that holds its outputs and capture sessions through device
synchronization, verifies finite logits, and compares outputs and captures
using `torch.equal` without tolerance. This is numerical comparator equality,
not a raw-bit guarantee. Validate every timed output's shape, dtype, device
and finiteness, and the expected event count and 3,072-byte capture for the two
capture modes. Run model forwards under `torch.no_grad()` with autocast
disabled, except for the narrowly scoped local autograd readout used by the
gradient mode. Seed the PyTorch CPU and CUDA RNGs with 17. Bound each capture
session to two events and 64 KiB; these caps exclude temporary tensors and
workspaces. Each captured sample must match the preflight's module path and
kind, layer and forward/invocation indices, output selector, batch/token
selection, event sequence, run identity and mode, as well as its layout and
byte count. Timed samples do not independently re-establish equality to the
preflight output.

## Prespecified schedule

Plan five separate, freshly spawned owner processes, numbered 0 through 4.
Each loads the pinned checkpoint and performs the preflight independently. Run
two warmup rounds on the same timed and validated path, then **12 measured
rounds**; exclude warmup timings from the summaries. A round contains one
sample of each of the three modes. Warmup order is `none, direct, gradient`,
then `gradient, direct, none` in every session.

For each measured session, start with the following ordered list of the six
possible mode permutations, repeated twice. Shuffle that 12-item list with a fresh Python
`random.Random(seed)`, using the respective seeds 53101, 53102, 53103, 53104,
and 53105. The frozen 60-round [schedule](../evidence/gpu-tap-latency-repeated-v1/schedule.json)
was generated by the [committed generator](../scripts/generate_gpu_tap_repeated_schedule.py).
Record the generating Python version. The frozen schedule bytes are
authoritative if a later Python version changes its shuffle implementation.
Each mode then occurs four times in each position in every session.

1. `none, direct, gradient`
2. `none, gradient, direct`
3. `direct, none, gradient`
4. `direct, gradient, none`
5. `gradient, none, direct`
6. `gradient, direct, none`

Launch at most these five scheduled attempts. Do not replace, omit or rerun a
session based on its timing or contamination status. Preserve any failed or
unverified attempt with its original position, stage and partial records. A
material implementation or protocol correction requires a new, published
revision and a separately identified experiment; it must not silently replace
these attempts. Do not pool the earlier v2 observations into this analysis.

The device may be released between owners so other reviewed GPU workloads can
run. Each owner needs an explicit coordinated project quiet window for its
short timing interval, with start and end announced to all participating
CPU-intensive/model and GPU-work owners. Other light work may continue. This
coordination cannot establish system-wide CPU quiescence or exclude desktop
GPU activity, and it must not close or terminate the user's applications.

## Timing, activity screen and admission

Use `perf_counter_ns` for wall intervals and all monitoring/endpoint time
tags; record `time.get_clock_info('perf_counter')`. Require a monotonic clock
with finite positive reported resolution at most 1 microsecond and a positive
sample interval of at least 100 reported resolution units. Record separate
CUDA event spans on the explicitly checked default stream. Synchronize the
device at the same boundaries as the reference implementation, retain output
and capture objects through the completion synchronization, dispose them,
then synchronize before post-sample memory observations. Wall time is the
primary latency and includes event recording, the forward, hook/readout,
output validation, completion synchronization, disposal and final
synchronization. Pre/post memory guards and subsequent journal writes are
outside that interval. The event span is a secondary device-stream interval
and may include host-induced gaps or omit unjoined stream work. Journal
flush/fsync occurs after each sample interval, but it and NVIDIA polling can
perturb later samples; mode order can also have carryover effects despite the
balanced schedule. Record monitoring query intervals as descriptive context,
without post hoc exclusions or reweighting based on overlap. The clock rule
bounds nominal resolution, not total timing accuracy.

Use the v2 activity classifier and its complete-coverage rules for the span
from preflight through the last measured sample: three valid idle observations
before and three after, no
query errors, bounded query start/end times and gaps, stable device identity
and total, and before/after process queries bracketing the workload. Initial
telemetry and process queries must be valid and fresh before the first
preflight forward; stop before sampling on unavailable or malformed initial
data. Keep the strict distinction between screen **status** and **availability**:
a foreign listed GPU PID or idle utilization above 5% is contamination, while
an error, identity mismatch or inadequate coverage makes availability
unverified even if the status is also contaminated. Do not promote an
unavailable screen as a completed comparison.

Permit completed contaminated sessions only as explicitly exploratory
observations. Preserve both contamination reasons, all sampled utilization and
endpoint process details privately. Report the number of distinct foreign PIDs
and the sampled values publicly without asserting that listed processes were
actively computing; WDDM endpoint lists and sampled utilization can miss or
misattribute activity. An after-idle utilization sample's averaging window may
overlap preceding benchmark work. Neither a clean screen nor a cooperative
lease proves physical exclusivity.

Run each owner under the common canonical physical-device lease and reviewed
supervisor, with source and pinned assets checked before use. Bind all five
attempts to one committed source, host/device, driver and runtime settings;
a mismatch is a failed attempt, not a reason to silently pool different
conditions. Reproduce the
reference's 25% native PyTorch allocator cap/readback, whole-run memory
commitment, 128 KiB aggregate trace claim, reserve/headroom and remaining-cap
checks, and conservative allowance for non-PyTorch CUDA allocations. Require
at least 3 GiB free before model transfer, `reserved <= cap - 256 MiB`, and
device-free headroom of at least `max(1 GiB, ceil(15% of total)) + 256 MiB
headroom + 256 MiB outside-cap allowance + max(0, cap - reserved)`. Bind
actual total and selected/runtime device identity before transfer; recheck live
headroom immediately before weight copy, input allocation, preflight and each
sample. These are provisional admission guardrails and sampled observations,
not a physical reservation or guaranteed peak. The prior two-token pilot is
supporting evidence, not a general workload profile. Hold the whole-run memory
and trace claims through verified synchronized disposal; hold the physical
device lease through the owner process lifetime and retain supervisor control
until it is reaped. On successful teardown, attest clean only after synchronized
disposal and claim release, while the physical lease is still held; the parent
then verifies the child exit and reap.

Recheck the owner session immediately before each CUDA-facing or telemetry
boundary. On unsafe pressure or failure, preserve diagnostics and attempt a
drain only while ownership remains valid. If synchronization fails or is
interrupted, or ownership is lost, latch completion as unverified and make no
further CUDA calls; retain the model, outputs, claims and exception custody
until process termination, with the sticky unsafe marker left in place. Never
attest clean or release those claims merely because a failure was recorded.
This sticky failure rule is a new requirement: do not copy the older reference
owner's unconditional failure-drain behavior. Any additional checks included
inside a timed interval must be identical across modes and documented.

## Analysis and evidence

For each completed session and each measured round, compute synchronized wall
time `gradient/direct`, `direct/none`, and paired millisecond differences
`gradient - direct` and `direct - none` from that round. The primary session
statistic is the median of its 12 gradient/direct ratios; `statistics.median`
averages the two middle ratios. The overall descriptive statistic, if at least three sessions are
complete, is the median of their session medians. Also report every session
median and its range, complete-session count, per-session screen status and
availability, and all per-round values. A complete session has a passing
preflight, all six warmup samples and all 36 measured samples in the frozen
order, exactly one passed postcheck per observation, a cleanly reaped owner and
an available activity screen. A partial round or a pending, failed, missing,
duplicate or orphan postcheck leaves that session incomplete. Show `no_contamination_observed`
and contaminated sessions separately, as well as the prespecified descriptive
aggregate of all complete sessions; label that aggregate exploratory if it
includes any contaminated session. Never hide failed attempts or select
sessions by their timing. The secondary summaries use the same rule for
direct/none and paired differences. Report per-mode wall and CUDA-event
medians per session; any overall value is the median of the session medians,
not a pooled per-sample median.

Five same-device sessions close in time are not independent samples of other
hosts, inputs, or desktop conditions. The session range is descriptive, not a
confidence interval. Complete-case results are conditional on the sessions
that finished and are not corrected for failures or contamination; failures
related to device load can bias them. System CPU scheduling and GPU clock,
power and thermal state are uncontrolled and may drift between sessions.
Record available context without treating it as proof of isolation. Do not make
a hypothesis-test, stable percentage slowdown, or general speedup claim from
this experiment. If fewer than three sessions complete, report the individual
completed sessions and no aggregate ratio.

For every attempt, save the frozen schedule, source commit and hashes, model
asset hashes, actual software/backend and device settings, clock properties,
owner/supervisor lifecycle, live allocator and device-free snapshots, raw
ordered warmup/measured observations and their separate passed or failed
postchecks, telemetry, screen reasons, and cleanup outcome. Never promote a
pending observation as completed. Preserve partial data on failure. The full
private evidence retains process PIDs, names and device identity for local
replay; any public subset must omit those fields, have its own file inventory,
and explain which identity comparisons it cannot independently reconstruct.

Before GPU execution, independently review the exact-source implementation,
fake-device synchronization and failure paths, including lost ownership and
failed/interrupted drains with no subsequent CUDA calls, parent evidence replay,
privacy projection, schedule generation, and statistic recomputation. The
implementation must enforce workload admission before any GPU launch.
