# Isolated CUDA capture benchmark, protocol v1

Status: protocol and harness under construction; **GPU execution is disabled until the shared supervisor is integrated and reviewed**, and no result is asserted by this document. Preserve any earlier results. This protocol measures one forward workload in a reserved device window. It is not a shared-service throughput test, a training-step benchmark, or an explanation of model behavior. Shared-load throughput, queueing and fairness need their own concurrent workload protocol.

## Question and fixed workload

How much additional end-to-end time and memory does ID-only, direct, or isolated-gradient capture cost at matched transformer positions compared with an uninstrumented forward? The gradient channel reads an already-available activation and cannot supply extra information merely by re-encoding it. No performance advantage is assumed.

- Model: `distilbert/distilgpt2`, immutable revision `2290a62682d06624634c1f46a6ad5be0f47f38aa`, using the repository's offline pretrained loader, which verifies the weights hash. Eager evaluation, float32, `no_grad`, no KV cache, batch size one; no text, gradients, activations, or weights are written to the result directory.
- Input: token IDs `[15496, 11, 616, 1438, 318, 257, 1332, 13]`; save their canonical JSON SHA-256. Record every model, library, backend, deterministic setting and source revision. Hardware and free memory must be inspected on the executing machine, not assumed from its nominal model.
- Capture: block, attention and MLP outputs on all six layers, selected batch position 0 and token positions 0, 3 and 7. Each mode uses the same points and selection. The trace stays on its source device; there is no CPU offload. Enforce both 32 event and 4 MiB retained-value limits. Before loading weights, reserve the larger of 1 GiB and 15% of total VRAM, budget twice the model parameter/buffer size plus 256 MiB and the trace limit, and set a PyTorch per-process allocator cap. Before each trial, check the cooperative lease and device-wide free memory against the reserve plus 256 MiB and the trace limit. These snapshots and allocator limits cannot prevent every transient or other process allocation. On an unsupported shape, missing tap, capacity excess, memory pressure or OOM, fail the run rather than changing the workload.
- Preflight: after loading, compare model outputs across all modes exactly including dtype, shape and device; compare ordered source metadata, event identity and selected positions; and require exact direct/gradient values, saved tensor layout and retained-byte equality. Require exactly the frozen 18 layer/role locations, each called once. These checks happen outside the timing sample and do not establish task-level training transparency or causal validity.

The full run uses ordering seeds 17, 29, 43 and 71, with 10 warmup rounds and 30 measured rounds per seed. Each round shuffles all four modes once; save the seed, round, position and every sample. Inputs and model remain fixed, so these are correlated repeats on the same model and input, not independent models or data. A `--quick` run uses only seed 17, one warmup round and three measured rounds and must be labeled a smoke run. The protocol is bounded; run a quick check and inspect memory before a full run. The CPU unit tests do not constitute a CUDA measurement.

## Timing boundaries

`none` is the **forward-only** baseline. The other modes are **complete forward-plus-capture** operations: attach hooks; forward; validate, capture or compute the gradient readout; construct event metadata; count retained bytes; remove hooks; synchronize while the output and trace are still alive; dispose the output and trace; synchronize again. The uninstrumented output is held to the same completion boundary and disposed on the same schedule. No optimizer, task backward, trace-tensor offload to the host or model loading is timed. The finite-value checks do transfer a reduction scalar to the host and synchronize, and their cost is included. Synchronize the selected device before starting each wall-clock interval and before reading the CUDA event pair. Every sample is synchronous end-to-end wall time, in nanoseconds, including Python and synchronization overhead. It is not enqueue-only timing.

CUDA events, recorded on the default stream before the operation and after hook removal but before the completion synchronization and disposal, provide a second, separately labeled span. They are not pure kernel-time sums: CPU hook work, value-validation synchronizations and delayed kernel submission can create device idle gaps inside the span. This protocol uses eager default-stream execution, not work launched on unjoined custom streams. Both channels include the implementation's finite-value validation; it converts a reduction to a Python boolean at each value tap and therefore synchronizes CUDA. Both use advanced indexing to select positions, creating an owned copy; direct mode retains that copy, while the gradient path additionally clones it and runs the isolated autograd readout. Neither cost may be omitted or attributed solely to gradient formation. Keep raw wall and event values; summaries are descriptive and do not claim general hardware speedups. Before observing results, define each comparison as the median of per-round wall-time ratios: ID/none, direct/none and gradient/direct within the same seed and round. They are correlated comparisons, not independent trials or confidence intervals; also report each mode's median wall and CUDA-event time.

## Memory and device isolation

Reset PyTorch peak counters before each sample. Record the selected process's current allocated and reserved bytes before the sample, its peak allocated and peak reserved bytes during it, and its post-disposal values. These allocator counters include the resident model and caching behavior, but exclude CUDA context, non-PyTorch allocations and other processes; a reserved-memory peak is not a count of live tensors. Cached reservations can carry over from earlier modes, so interpret each peak with its entry baseline and randomized order, not as memory owned only by that mode. Record exact retained trace value bytes separately, which are not peak memory.

Record `torch.cuda.mem_get_info` device-wide free/total snapshots immediately before and after each timed sample. In addition, sample `nvidia-smi` periodically in a separate monitoring process and save the raw observations and timestamps, query failures, configured interval and actual intervals. Match the selected GPU to its recorded UUID and driver. Use a shared monotonic clock to align telemetry and measured rows. The minimum sampled free and maximum sampled used are **sampled extrema, not a true device-wide peak**; transient peaks and foreign activity can be missed. Polling itself may affect the latency being measured; it is part of the recorded measurement environment. Process-list information on Windows WDDM can be incomplete; exclude the benchmark's own PID from foreign-process checks. None of these observations proves the GPU was idle throughout the run.

Before running, drain the broker and coordinate with all experiment teams. The dedicated benchmark process must acquire the same cooperative device lease used by the broker, before touching CUDA, and retain it until process exit. The lock controls cooperating processes only; it cannot stop external desktop applications. `--exclusive` separately records the operator's explicit attestation that the coordinated workload is drained. Screen activity using at least three device-utilization samples before the workload and three at least one second after it ends; a sample over 5% in either idle screen, a detected other compute process, missing telemetry, any query error, a gap over two seconds in coverage, an unverified GPU UUID mapping, or no attestation marks the run **unverified or contaminated**. Process lists are endpoint snapshots and can miss transient processes. Report the reason and do not present it as uncontended. Even a passing screen is only “no contamination observed” and does not prove isolation. Record GPU identity, driver, OS, CUDA visibility and telemetry limitations alongside the raw data.

## Failure, reproducibility and output

Use a newly created output directory; never overwrite an old run. Before work, create a started marker and immutable source archive; append and fsync every completed measurement to a JSON-lines progress journal outside the timed interval. Journal I/O can influence system load and spacing between trials, so it is part of the recorded environment. If a process dies, an existing started marker with neither a success nor failure marker identifies an incomplete run; only complete journal lines are recoverable. Save full raw timing rows, telemetry, prespecified configuration, environment, hashes of verified model assets including configuration, loaded Python module hashes, Git revision and dirty state/diff identity, preflight checks, isolation status and descriptive summaries. Record Python, Torch, Transformers, CUDA, cuDNN, driver, GPU UUID, visibility mapping and TF32/determinism/backend settings. Python/native extension module hashes do not include every loaded DLL, so exact dependency replay is not guaranteed. No precision or tap substitution is permitted. An exception, cancellation or OOM produces a failure artifact, retains completed partial samples when possible and never writes a successful results summary. Treat OOM recovery as a fresh process and a separately labeled run. Missing dependencies or inaccessible telemetry must be recorded; an inability to screen makes latency comparisons unverified. Fixes or configuration changes require a new labeled run; do not silently pool different protocol versions.

Terminal evidence includes byte counts and SHA-256 digests for the other files in its output directory; `verify_artifact_inventory` detects ordinary missing, added or altered files. This local inventory is not an authenticated registry seal: someone able to rewrite or delete the terminal record can forge a consistent inventory or erase the outcome. The separate experiment registry offers its own manifest and lifecycle rules; the benchmark does not claim that its incremental journal is already sealed by that registry.

The only execution inputs are a local cache containing the pinned verified checkpoint, a new output path, an absolute shared lease path, and an attested reservation flag. No model download is performed by this benchmark. Exact commands and checked evidence will be recorded with any completed result.
