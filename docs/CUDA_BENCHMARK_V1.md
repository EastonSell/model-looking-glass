# Isolated CUDA capture benchmark, protocol v1

Status: protocol and harness under construction; **GPU launch is explicitly disabled until resource admission for this exact eight-token, 18-event capture workload is independently reviewed**, and no result is asserted by this document. A two-token service profile is not admission for this workload. CPU preflight and the supervised owner/controller tests remain available. Preserve any earlier results. This protocol measures one forward workload in a reserved device window. It is not a shared-service throughput test, a training-step benchmark, or an explanation of model behavior. Shared-load throughput, queueing and fairness need their own concurrent workload protocol.

## Question and fixed workload

How much additional end-to-end time and memory does ID-only, direct, or isolated-gradient capture cost at matched transformer positions compared with an uninstrumented forward? The gradient channel reads an already-available activation and cannot supply extra information merely by re-encoding it. No performance advantage is assumed.

- Model: `distilbert/distilgpt2`, immutable revision `2290a62682d06624634c1f46a6ad5be0f47f38aa`, using the repository's offline pretrained loader, which verifies the weights hash. Eager evaluation, float32, `no_grad`, no KV cache, batch size one; no text, gradients, activations, or weights are written to the result directory.
- Input: token IDs `[15496, 11, 616, 1438, 318, 257, 1332, 13]`; save their canonical JSON SHA-256. Record every model, library, backend, deterministic setting and source revision. Hardware and free memory must be inspected on the executing machine, not assumed from its nominal model.
- Capture: block, attention and MLP outputs on all six layers, selected batch position 0 and token positions 0, 3 and 7. Each mode uses the same points and selection. The trace stays on its source device; there is no CPU offload. Enforce both 32 event and 4 MiB retained-value limits. Before loading weights, reserve the larger of 1 GiB and 15% of total VRAM, budget twice the model parameter/buffer size plus 256 MiB and the trace limit, and set a PyTorch per-process allocator cap. Before each trial, check the cooperative lease and device-wide free memory against the reserve plus 256 MiB and the trace limit. These snapshots and allocator limits cannot prevent every transient or other process allocation. On an unsupported shape, missing tap, capacity excess, memory pressure or OOM, fail the run rather than changing the workload.
- Preflight: after loading, require finite model outputs in every mode and compare them with `torch.equal`, including explicit dtype, shape and device checks; compare ordered source metadata, event identity and selected positions; and use the same comparator for direct/gradient values, with saved tensor layout and retained-byte equality. `torch.equal` applies numeric equality without an explicit tolerance, not bitwise identity: positive and negative zero compare equal, and subnormal handling can depend on the backend. The persisted `outputs_exact` and `values_exact` fields refer to this comparator, not bytewise comparison. Require exactly the frozen 18 layer/role locations, each called once. These checks happen outside the timing sample and do not establish task-level training transparency or causal validity.

The full run uses ordering seeds 17, 29, 43 and 71, with 10 warmup rounds and 30 measured rounds per seed. Each round shuffles all four modes once; save the seed, actual schedule seed, round, position and every warmup and measured sample. Warmup rows are retained separately and excluded from timing summaries. Inputs and model remain fixed, so these are correlated repeats on the same model and input, not independent models or data. A `--quick` run uses only seed 17, one warmup round and three measured rounds and must be labeled a smoke run. The protocol is bounded; run a quick check and inspect memory before a full run. The CPU unit tests do not constitute a CUDA measurement.

## Timing boundaries

`none` is the **forward-only** baseline with the same output validation used in every mode. The other modes are **complete forward-plus-capture** operations: attach hooks; forward; validate, capture or compute the gradient readout; construct event metadata; count retained bytes; remove hooks; synchronize while the output and trace are still alive; dispose the output and trace; synchronize again. Every warmup and measured sample checks the output layout and finiteness; this common output reduction and its host synchronization are included in the timing for all four modes. Every instrumented sample also checks all 18 ordered identities, source and saved layouts, and retained bytes against the frozen preflight. These checks, per-target pre-call and completion hooks, invocation tracking and model-ownership checks are included in the measured adapter overhead. The uninstrumented output is held to the same completion boundary and disposed on the same schedule. No optimizer, task backward, trace-tensor offload to the host or model loading is timed. The finite-value checks do transfer a reduction scalar to the host and synchronize, and their cost is included. Synchronize the selected device before starting each wall-clock interval and before reading the CUDA event pair. Every sample is synchronous end-to-end wall time, in nanoseconds, including Python and synchronization overhead. It is not enqueue-only timing.

CUDA events, explicitly recorded on the selected device's default stream before the operation and after hook removal but before the completion synchronization and disposal, provide a second, separately labeled span. The runner checks the current stream at the beginning and end of each sample and primes events on that same default stream. The span can omit work transiently submitted to unjoined custom streams; device-wide synchronization still waits for its completion in wall time. Events are not pure kernel-time sums: CPU hook work, value-validation synchronizations and delayed kernel submission can create device idle gaps inside the span. Both channels include the implementation's finite-value validation; it converts a reduction to a Python boolean at each value tap and therefore synchronizes CUDA. Both use advanced indexing to select positions, creating an owned copy; direct mode retains that copy, while the gradient path additionally clones it and runs the isolated autograd readout. Neither cost may be omitted or attributed solely to gradient formation. Keep raw wall and event values; summaries are descriptive and do not claim general hardware speedups. Before observing results, define each comparison as the median of per-round wall-time ratios: ID/none, direct/none and gradient/direct within the same seed and round. They are correlated comparisons, not independent trials or confidence intervals; also report each mode's median wall and CUDA-event time.

## Memory and device isolation

Reset PyTorch peak counters before each sample. Record the selected process's current allocated and reserved bytes before the sample, its peak allocated and peak reserved bytes during it, and its post-disposal values. Reject negative or inconsistent timing, allocator peaks, or device-memory snapshots before recording a row. These allocator counters include the resident model and caching behavior, but exclude CUDA context, non-PyTorch allocations and other processes; a reserved-memory peak is not a count of live tensors. Cached reservations can carry over from earlier modes, so interpret each peak with its entry baseline and randomized order, not as memory owned only by that mode. Record exact retained trace value bytes separately, which are not peak memory.

Record `torch.cuda.mem_get_info` device-wide free/total snapshots immediately before and after each timed sample. In addition, a monitoring thread periodically starts `nvidia-smi` subprocesses and saves the raw observations, query start/end timestamps, failures, configured interval and actual intervals. Invalid or inconsistent total, used or free values make the isolation screen unverified; used plus free need not equal total because of driver reservation and MiB rounding. Verify the selected GPU against its physical UUID and driver. All `*_monotonic_ns` measurement, telemetry, workload and start fields use the shared `time.perf_counter_ns()` clock; record its implementation and resolution. This high-resolution monotonic clock avoids the coarse `monotonic_ns()` resolution on this Windows/Python version. Timeout deadlines use a separate clock and are not compared with those fields. The minimum sampled free and maximum sampled used are **sampled extrema, not a true device-wide peak**; transient peaks and foreign activity can be missed. Polling itself may affect the latency being measured; it is part of the recorded measurement environment. Process-list information on Windows WDDM can be incomplete; exclude the benchmark's own PID from foreign-process checks. The driver may average utilization over overlapping windows, so consecutive idle samples are not independent idle intervals. None of these observations proves the GPU was idle throughout the run.

Earlier source revisions used `time.monotonic_ns()` for these same field names.
Interpret saved timestamps using their recorded source revision and clock
metadata; do not subtract or pool timestamps across clock domains.

Before running, drain the broker and coordinate with all experiment teams. The dedicated benchmark process must acquire the same cooperative device lease used by the broker, before touching CUDA, and retain it until process exit. The lock controls cooperating processes only; it cannot stop external desktop applications. `--exclusive` separately records the operator's explicit attestation that the coordinated workload is drained. Screen activity using at least three device-utilization queries completed before the workload and three begun at least one second after it ends. Across the whole screen, conservatively bound each unknown gap using the next query's end and the previous query's start; a bound over two seconds marks the run unverified. A sample over 5% in either idle screen, a detected other compute process, missing telemetry, any query error, an unverified GPU UUID mapping, or no attestation also marks the run **unverified or contaminated**. Process lists are endpoint snapshots and can miss transient processes. Report the reason and do not present it as uncontended. Even a passing screen is only “no contamination observed” and does not prove isolation. Record GPU identity, driver, OS, visibility restrictions and telemetry limitations alongside the raw data.

## Failure, reproducibility and output

Use a newly created output directory; never overwrite an old run. The parent records its start before a separate CPU-only offline checkpoint and trace preflight. A supervised child accepts the parent-created directory only when its start marker and parent identity match. The owner saves an immutable source archive, then appends and fsyncs every completed measurement to a JSON-lines progress journal outside the timed interval. Journal I/O can influence system load and spacing between trials, so it is part of the recorded environment. A start marker without a success or failure terminal identifies an incomplete run; only complete journal lines are recoverable. Failure counts and partial CSVs cover rows acknowledged after fsync; a complete-looking final journal line after a write, flush or fsync error has unknown durability. Save full raw timing rows, telemetry, prespecified configuration, environment, hashes of verified model assets including configuration, loaded-module file hashes, Git revision and dirty state/diff identity, preflight checks, isolation status and descriptive summaries. These hashes describe files found at loaded module paths, not a complete attestation of in-memory code. Record Python, Torch, Transformers, CUDA, cuDNN, driver, the verified mapping policy and TF32/determinism/backend settings. Native DLLs are not comprehensively hashed, so exact dependency replay is not guaranteed. No precision or tap substitution is permitted. An exception, cancellation or OOM retains failure evidence and completed partial samples when possible, and never writes a successful results summary. Treat OOM recovery as a fresh process and a separately labeled run. Missing dependencies or inaccessible telemetry must be recorded; an inability to screen makes latency comparisons unverified. Fixes or configuration changes require a new labeled run; do not silently pool different protocol versions.

Terminal evidence includes byte counts and SHA-256 digests for the other files in its output directory; `verify_artifact_inventory` detects ordinary missing, added or altered files. Publication uses an atomic no-clobber link: once a terminal exists it remains authoritative even if cleanup of its temporary `.partial` link fails. Unsealed `.partial` scratch files are excluded from the inventory and may remain after interrupted cleanup. This local inventory is not an authenticated registry seal: someone able to rewrite or delete the terminal record can forge a consistent inventory or erase the outcome. The separate experiment registry offers its own manifest and lifecycle rules; the benchmark does not claim that its incremental journal is already sealed by that registry.

The execution inputs are a local cache containing the pinned verified checkpoint, a new output path, one absolute GPU-coordination workspace root shared by all worktrees, and an attested reservation flag. The bounded `cpu_preflight.json` records the completed CPU check even when GPU admission is unavailable; the supervised child receives its digest and checks the saved bytes before starting. The UUID-derived lease and unsafe marker remain private coordination state. The owner must verify its actual CUDA binding and drain, retain its lease until exit, and receive a clean supervisor attestation before the parent publishes a terminal outcome. A failed experiment and unsafe device teardown are separate states. On Windows, the owner uses the base Python executable as the direct supervised child with the selected environment's package directory; its actual interpreter, package locations and file hashes are recorded. Controller and direct children require Python 3.11+, `-I -B -S`, and a fresh nonexistent `-X pycache_prefix`. These prevent inherited Python-path/startup hooks and stale timestamp-valid bytecode from being selected at startup. The source-first controller entrypoint below validates those flags before importing project code. `-I` ignores `PYTHONHASHSEED`; do not claim a fixed Python hash seed. Explicit model and ordering seeds remain recorded. This does not authenticate code or prevent same-account mutation. No model download is performed by this benchmark.

Invoke the controller source file directly, replacing the placeholders with absolute local paths and choosing a fresh cache-prefix path that does not exist:

```text
python -I -B -S -X pycache_prefix=<fresh-path> looking_glass/cuda_benchmark_entry.py --site-packages <venv-site-packages> --output <new-run-directory> --workspace-root <shared-gpu-root> --cache-dir <offline-hf-cache> --quick --exclusive
```

The controller validates the startup flags and dependency directory before importing the benchmark. Its CUDA launch still stops at the explicit admission gate above.

The source entrypoint loads the project package from its explicit source path without adding the repository root to the top-level import search, places the selected dependency directory after the standard library, and rejects sourceless Python imports and native replacements of project modules handled by the standard path finder. An imported dependency may install another fallback finder, which the present guard does not constrain. Before the GPU gate may be enabled, independently review all remaining dependency origins and fallback finders, constrain or reject inherited CUDA, allocator and TF32 controls through the real supervisor, read back the actual allocator backend and limit, and bind those settings to the exact workload's resource admission. The current source-first flags alone do not establish those properties.

Physical GPU UUIDs and raw CUDA visibility are removed from persisted JSON, CSV and journal evidence, but other local paths, process details or exception messages may contain private machine information. Treat result directories as local evidence and review or sanitize a proposed public copy before committing it. Redaction does not by itself make a result directory safe for public release.
